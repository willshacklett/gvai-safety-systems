# Private staging application V1

## Boundary

This is a runnable, invite-only **advisory** application, not a deployment or
commercial launch approval. Evaluation responses retain `advisory_only=true`
and `enforcement_applied=false`. The customer workload is not controlled by this
API. There is no signer, production checkpoint, SQLite grant, recovery authority,
billing, signup, dashboard, or supervisor STOP wiring.

[Application source](../gvai/private_staging.py) reuses the existing
[PostgreSQL backend](commercial_advisory_backend_v1.md), customer-key lifecycle,
commercial service, evaluator, and bounded [HTTP server](commercial_http_v1.md).
No new database schema or public provisioning endpoint is installed.

## Process and credential separation

- Runtime has only its restricted PostgreSQL role and customer-key verifier
  secret. It never loads operator credentials. Startup rejects superuser,
  role-management, replication, bypass-RLS, owner/member, schema/database CREATE,
  table/column/sequence access, and non-entry authority function privileges.
- The three advisory entry functions must be security-definer functions owned
  by the non-superuser authority owner, with the existing pinned search path.
  Installed `pgcrypto` extension functions retain their existing permissions;
  this exception does not include reservation or provisioning functions.
- Provisioning, revocation and suspension run as a separate operator command
  using the non-superuser authority owner. Customers cannot choose tenant,
  principal, project, quota or expiry during provisioning. Identifiers are
  generated by the operator tool; the operator config fixes every new pilot's
  cap and duration (maximum 1,000 units and 30 days).
- `suspend` disables the tenant independently of **all** its customer keys,
  denying new evaluations and usage reads. Keys need not be revoked first.
  There is deliberately no automatic unsuspend command. This is customer
  suspension, not an independent whole-service STOP implementation.
- Use separate OS accounts and protected directories for runtime and operator.
  The runtime account must not be able to read the operator file, handoff files,
  container credentials, backups, or database administration interfaces.
  Do not colocate operator and runtime secrets in one environment file.

## Explicit private configuration

Only loopback HTTP (`127.0.0.1`) and explicitly configured loopback PostgreSQL
are supported. No bind-host switch, public URL, automatic environment fallback,
migration runner, authority initialization or trust bootstrap is provided.
Remote private database access requires a separately managed loopback tunnel;
network topology, TLS, tunnel supervision and firewall review are operational
prerequisites, not automatically supplied.

Install declared optional runtime dependencies in an approved environment:

```sh
python -m pip install -r requirements-private-staging.txt
```

Create the following **outside the repository**, in directories owned by the
appropriate process account with mode `0700`. Every JSON file must be a regular
file owned by that account, have no group/world permissions (`0600` or `0400`),
and be at most 16 KiB. Symlink final components, duplicate fields, non-finite
numbers, missing/unknown config fields, and permissive file modes are rejected.
Placeholders below are not usable credentials; supply separately provisioned
development values. Do not put real secrets in shell arguments or source.

Runtime file:

```json
{
  "mode": "private-staging",
  "database_dsn": "host=127.0.0.1 port=5432 dbname=PRIVATE_DB user=RESTRICTED_RUNTIME password=PRIVATE_PASSWORD",
  "verifier_secret_hex": "REPLACE_WITH_SEPARATELY_PROVISIONED_32_BYTE_HEX_SECRET",
  "authority": {
    "authority_id": "EXPLICITLY_PROVISIONED_AUTHORITY",
    "epoch": 1,
    "trust_domain": "PRIVATE_TRUST_DOMAIN"
  },
  "port": 8080,
  "max_connections": 8
}
```

Operator file, readable only by the operator account:

```json
{
  "mode": "private-staging-operator",
  "operator_database_dsn": "host=127.0.0.1 port=5432 dbname=PRIVATE_DB user=NON_SUPERUSER_AUTHORITY_OWNER password=PRIVATE_PASSWORD",
  "verifier_secret_hex": "THE_SAME_INDEPENDENT_CUSTOMER_VERIFIER_SECRET",
  "pilot_units": 100,
  "pilot_seconds": 604800
}
```

Apply reviewed migrations 001-003 and explicitly provision the authority
identity beforehand, as described in the backend document. Runtime gets only
schema USAGE and the three advisory entry EXECUTE grants. DSNs must include a
single `host=127.0.0.1`, database, user and password; service/passfile/SSL private
key/options overrides are rejected. Connection, statement and lock timeouts
cannot be overridden through configuration.

Commands (paths contain no secrets):

```sh
python -m gvai.private_staging --config /private/operator.json provision \
  --key-output /private/customer-one-handoff.json
python -m gvai.private_staging --config /private/runtime.json serve
python -m gvai.private_staging --config /private/operator.json revoke --key-id KEY_ID
python -m gvai.private_staging --config /private/operator.json suspend --tenant TENANT_ID
```

Provisioning writes generated tenant/principal/project IDs, key ID, expiry and
one-time credential to a newly created mode-0600 file, never stdout or logs.
It refuses existing output paths, including symlinks, instead of overwriting a
secret. Deliver through a separately reviewed private channel; remove the
handoff copy after delivery. Provisioning and key insertion reuse separate
durable transactions: any failure or lost acknowledgement requires operator
reconciliation, not an automatic retry. A failed/partial handoff file may be
empty or incomplete and must not be treated as issuance success. Inspect
durable tenant/key state and revoke unrecoverable keys before creating a new
pilot or key. Suspension/revocation report failure when confirmation is absent.

## HTTP contract

All responses are JSON, close the connection, and use `Cache-Control: no-store`.
The inherited server bounds headers (16 KiB/32 headers), request bodies
(16 KiB), simultaneous handlers (16), and network I/O deadline (5 seconds).
It does not log request headers, URLs or bodies. Do not configure proxy access
logs to include credentials or request/response payloads.

| Endpoint | Authorization | Result |
|---|---|---|
| `POST /v1/evaluations` | Bearer customer key; `evaluation:run` and current project ownership | Existing advisory response; request `"version":"v1"` |
| `GET /v1/usage/PROJECT_ID` | Bearer customer key; `usage:read` and current project ownership | Lifetime cap, consumed/reserved/completed/failed/remaining; advisory flags |
| `GET /healthz` | Loopback-only; no customer identity needed | Fixed `status=ok`; liveness only |
| `GET /readyz` | Loopback-only; no customer identity needed | Fixed `status=ready` (200) or `unavailable` (503), advisory flags |

GET bodies, query parameters, percent-encoded project IDs, additional path
segments, and provisioning/key-management routes are unsupported. Missing
usage credentials return 401; unauthorized/expired/revoked/wrong-project keys
return the same 403. Database or inconsistent accounting state returns 503
without a fallback summary. Usage responses use `"version":1`.

Readiness actively checks a fresh connection and the runtime role/function
contract, not just process liveness. It does **not** authenticate checkpoint
history, test every customer's eligibility, consume a quota unit, or prove
the configured authority matches the current database head. Authority identity
is pinned by config and compared by the existing reservation path before any
evaluation. Readiness is never a grant, a restore-fence clearance, or a claim of
production rollback protection.

## Connection and shutdown behavior

`BoundedConnections` limits outstanding connections, including opens, to the
configured cap (1-32). Checkout waits at most 100 ms; exhaustion returns
unavailable. Each operation opens a fresh connection and closes it exactly
once. No idle pool, stale-session reuse or automatic transaction/commit retry
is implemented. Connect timeout is 3 seconds; PostgreSQL statement timeout
5 seconds, lock timeout 3 seconds and idle-in-transaction timeout 5 seconds.
These are per-operation bounds, not a whole-evaluation CPU deadline.

SIGINT/SIGTERM mark readiness unavailable and deny new database leases before
stopping HTTP acceptance and closing the listener. Existing leases drain for at most
10 seconds. Drain failure exits nonzero and is reported by a fixed redacted
event. Active handlers/calculations may lose completion or result delivery;
committed attempts stay charged and exact retries never re-evaluate. Shutdown
does not retroactively cancel committed advisory work or implement a
controlled-workload STOP. Startup failures close acquired resources and exit
nonzero. Operational logs contain fixed event names only, no exception traces,
credentials, DSNs or customer payloads.

## Private rollout and remaining blockers

1. Founder reviews code and real disposable-database results; no deployment
   occurs as part of this implementation.
2. Independently provision a development database, non-superuser owner,
   least-privilege runtime role and pinned advisory authority. Review migrations,
   operator custody and backup/reconciliation procedures.
3. Run the application locally, smoke-test liveness/readiness and an operator
   invitation, evaluate and read usage, then suspend the pilot and verify denial.
4. Only after separate approval, use an authenticated private tunnel/VPN and
   TLS ingress restricted to invited testers. Never expose this stdlib HTTP
   listener directly to the Internet.
5. Exercise database outage, capacity exhaustion and process shutdown; confirm
   redacted logging and no automatic ambiguous-accounting retries.

The next hosted-staging blocker is a reviewed **private ingress and operational
runbook**: TLS, authenticated network access, trusted proxy settings, redacted
metrics/alerts, rate limits, secret custody/rotation, backup reconciliation and
explicit suspension/STOP drills. There is no public customer signup, recurring
billing, reliable result redelivery, multi-replica connection budget, production
recovery fencing or live launch approval. Every replica would have its own
connection/handler cap; coordinate aggregate limits before scaling.

## Validation

Offline:

```sh
python -m pytest -q -p no:cacheprovider tests
```

Real PostgreSQL: use the approved disposable `postgres:16` procedure and opt-in
environment in [the backend document](commercial_advisory_backend_v1.md). The
existing integration suite now includes real private HTTP assembly/restart,
operator provisioning/suspension/revocation, scoped usage, capacity exhaustion,
connection refusal, privilege rejection and CLI SIGTERM. Offline runs explicitly
skip this suite and are not PostgreSQL evidence. Existing lost-acknowledgement
tests inject driver failures around real transactions; they are not an actual
network-partition claim.

Validated in the authorized development environment:

- **47 real integration tests passed** on official PostgreSQL 16.15 using
  non-superuser migration/runtime roles and temporary Python 3.14 dependencies.
- **716 offline tests and 362 subtests passed** using the existing approved
  Python 3.12 environment; the 47 integration tests were explicitly skipped
  offline and run separately against PostgreSQL.
- Changed Python files parse with Python 3.9 syntax; this is not a Python 3.9
  runtime certification. Exact 11-file scope, empty staging, final newlines and
  changed-line whitespace were checked.
